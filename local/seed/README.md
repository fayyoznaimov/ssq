# Мок-данные CRM: удалить всё, кроме админа, и залить тестовый набор

`wipe_and_seed.py` — одна транзакция на базе CRM: удаляет все данные схемы `public`, кроме служебных таблиц,
админа (`user.id = 1`) и того, что принадлежит самому этому аккаунту, затем записывает реалистичный тестовый
набор (сотрудники, воронка, клиенты, сделки с историей, задачи, письма, звонки), проверяет его и только тогда
делает `COMMIT`. Любая ошибка или непрошедшая проверка — `ROLLBACK`, и база остаётся **точно** как была,
последовательности (`*_id_seq`) и их комментарии тоже: в скрипте нет `setval` (он не откатывается), только
транзакционные `ALTER SEQUENCE … RESTART`, `COMMENT ON SEQUENCE` и `TRUNCATE … CONTINUE IDENTITY`.

`fingerprint.sql` — отпечаток данных только на чтение (число строк и md5 каждой таблицы без времени, хэшей паролей
и `token_version`, плюс метки диапазонов id на последовательностях): два запуска в один день дают одинаковые строки.

## Запуск

Скрипт работает на сервере, где есть контейнер Postgres `crm-db` (через `docker exec -i crm-db psql -U root`),
нужен Python 3.8+ с модулем `bcrypt` (на сервере есть). Принимает только `--db parisahon` (прод) или
`--db crm_staging`; любое другое имя (`crm_qa`, `parisahon_dev`, опечатка) — отказ до подключения к базе.

```sh
python3 wipe_and_seed.py --db crm_staging                       # только план: что удалится / останется, id; код 2
python3 wipe_and_seed.py --db crm_staging --rollback            # всё то же и проверки, в конце ROLLBACK: ничего не меняется
python3 wipe_and_seed.py --db crm_staging --i-have-a-backup     # стереть + залить + проверить, одна транзакция
docker restart crm2-staging                                     # кэши API в памяти — от старых данных
docker exec -i crm-db psql -U root -d crm_staging -X -q < fingerprint.sql
```

Пароли тестовых сотрудников — случайные, у каждой базы свои: `/root/crm2/seed/mock-users-<db>.txt`
(`mock-users-parisahon.txt`, `mock-users-crm_staging.txt`; каталог 700, файл 600). Нигде не печатаются; повторный
запуск на той же базе берёт пароли из её файла (логины не меняются), файл пишется только после `COMMIT`.

Параметры: `--container` (crm-db), `--db-user` (root), `--users-dir` (/root/crm2/seed), `--seed` (2026: тот же seed —
те же данные), `--inbox` / `--sent-mailbox` / `--spam-mailbox` / `--trash-mailbox` (папки почты = `EMAIL_*_MAILBOX`
API, по умолчанию `INBOX`, `INBOX.Sent`, `INBOX.spam`, `INBOX.Trash`), `--sql-out файл` (весь SQL изменения для
просмотра, chmod 600).

Скрипт отказывается менять базу без `--i-have-a-backup` (печатает план и выходит с кодом 2; `--rollback` — пробный
прогон, который ничего не оставляет) и не работает вовсе, если в базе нет таблиц `migrations`/`user`; `user 1` — не
живой админ; в схеме нет нужных колонок. Во время транзакции все таблицы заблокированы (`LOCK … ACCESS EXCLUSIVE`,
`lock_timeout` 20 с): API ждёт `COMMIT` пару секунд, ничего не вклинивается. После `--rollback` и после неудачного
запуска скрипт сам сравнивает все последовательности схемы (last_value, is_called, комментарий) и число строк
всех таблиц с тем, что было до запуска, и пишет результат (`sequences: all 41 exactly as before`); если что-то
отличается — предупреждение и код 1.

## Id: никогда не повторяются, последовательности только вперёд

Сервисы Telegram и WhatsApp держат живые сессии по `user_id` CRM, FTP-сервер — папки и пароли записей по
сотруднику, кнопки бота в Telegram несут id задач, очередь WhatsApp — id сделок; всё это вне базы и при очистке
не стирается. Поэтому:

- мок-строки каждой таблицы получают id **выше всего, что эта таблица когда-либо выдавала**: max(id) и позиция её
  последовательности, что больше, округлено вверх до сотни; с запасом на рост набора (`reserved to`);
- последовательность после записи ставится за конец диапазона (`ALTER SEQUENCE … RESTART`, только вперёд — назад
  никогда), на неё вешается комментарий `parisa-mock <first>-<last>`; новые настоящие строки получат id выше;
- повторный запуск видит этот комментарий и кладёт те же мок-строки в тот же диапазон (в нём никогда не было
  ничего, кроме мок-данных), поэтому два запуска дают одинаковые данные с одинаковыми id;
- таблицы, которые очищаются без заливки, — `TRUNCATE … CONTINUE IDENTITY` / `DELETE`: их последовательности
  не трогаются вовсе;
- под блокировками, до удаления, скрипт проверяет, что с момента плана id не ушли вперёд (иначе — откат и просьба
  запустить ещё раз), а после записи — что все мок-строки лежат в своём диапазоне.

План (и `--rollback`, и настоящий запуск) печатает диапазоны (`ids of the mock rows`) и **id сотрудников, чьи строки
удаляются**, с отметками, что у них есть в базе (`messengers telegram+whatsapp`, `CRM bot`, `recorder tokens`,
`call uploads`), строкой для копирования (`their user ids, to log out of the services: …`) и диапазоны удаляемых
контактов. По этому списку интегратор выводит их сессии из сервисов (см. «Продакшен»). На staging сейчас:
сотрудники 101–105, контакты 106–155 (метка `parisa-mock 101-200`), следующий новый пользователь получит id 201.

Порядок (блок PL/pgSQL читает каталог внутри транзакции, под блокировками, — подходит к той схеме, что в базе
сейчас): обнуляются ссылки оставляемых строк на удаляемое (строка, которой ссылка обязательна, удаляется с
сообщением), один `TRUNCATE … CONTINUE IDENTITY` всех таблиц, на которые не ссылаются оставляемые, `DELETE` чужих
строк частично оставляемых таблиц (`user` последней), `DELETE` из `company`/`group` (на них ссылается `user`).
Проверено на схеме коммита 436230d (staging: `timestamptz`, зона базы `Asia/Tashkent`, `ON DELETE RESTRICT`/`SET NULL`,
NOT NULL и CHECK, таблицы ИИ): время пишется в зоне сессии `Asia/Tashkent` (UTC+5), в JSON истории — в UTC с `Z`, как API.

### Как это выглядит живым

- **Скорость ответов** («Контроль ответов», аналитика менеджеров; норма 15 рабочих минут, 09:00–18:00 пн–сб):
  каждый сотрудник отвечает клиенту в своём темпе (`PACE`), доли раздаются равномерно по его ответам: ~80 % в
  пределах нормы, ~13 % в пределах часа, остальное позже (встреча, занятой день — такой ответ начинается с
  «Извините за задержку…»); сообщение вечером или в выходной — ответ утром в первые минуты рабочего дня или сразу
  с телефона. Сардор — слабее (~60 %). На staging: Морозов 77 %, Юсупова 78 %, Каримова 82 %, Турсунов 59 %, медиана
  ~9 минут; вся команда 73 % (в счёт входят и четыре вопроса, которые ждут ответа).
- **«Клиент ждёт ответа»** — как и раньше, у 4 открытых сделок клиент написал последним 5–10 дней назад (Оила Маркет,
  Домашний Уют Сибирь, Уютный Дом, Бишкек Текстиль Импорт); свежих (моложе 4 дней) неотвеченных сообщений нет —
  бот не шлёт напоминаний, автопилот не создаёт задач (проверка в транзакции).
- **Последовательность событий**: задача этапа ставится в его начале и закрывается после работы, о которой говорит
  её результат (КП отправлено — после письма с КП, «Договор подписан» — после сообщения клиента о подписи);
  обещанный звонок — в течение часа; груз приходит через свои дни в пути, потом звонок и оплата; примерно каждая
  пятая выполненная задача закрыта после своего срока.
- **«Срок поставки»** — из истории самой сделки: клиент называет его на выявлении потребности, у выигранной сделки
  он после отгрузки (товар пришёл в срок) и в прошлом, у проигранной — в прошлом, у открытой — в будущем; тот же
  срок в договоре и в переписке.
- **Поля сделки** (Цвет, Граммаж, Размер, Количество, Логотип, Страна поставки) — те же, что клиент написал в ТЗ,
  менеджер — в заметке «Потребность», и что стоит в КП; количество разных единиц — «500 компл. и 1 500 шт».
- **Русский язык**: у каждого города таблица падежей (`CITY`: в Москве / в Москву / до Москвы, в Бухаре / в Бухару /
  до Бухары, … в Бостанлыкском районе), глаголы прошедшего времени согласуются с полом говорящего, даты — «до
  24.10.2026» или «к 24 октября».
- **Разнообразие**: у каждого шага разговора 3–8 формулировок с фактами сделки (товар, размеры, плотность,
  количество, город, цена, номера КП, договора, счёта, ТТН); формулировки раздаются по сделкам равномерно, поэтому
  одна и та же фраза встречается не больше 4–5 раз на весь набор, у входящих обращений — разные первые сообщения.
- **Повторяемость**: всё содержимое зависит только от `--seed` и дня запуска: запуск в любое время того же дня даёт
  те же строки (проверено на 10 моментах каждого из 8 дней, от 00:01 до 23:59); в другой день сдвигаются даты, и
  может отличаться пара формулировок.

## Безопасность: ничто не уходит реальному человеку

- Телефоны только из несуществующих диапазонов: `+998 00 000 NN NN`, `+996 000 00 NN NN`, `+7 000 000 NN NN`
  (нормализатор API `helper/phone.ts` их принимает, последние 9 цифр уникальны).
- Почта только `@example.com/.org/.net` (зарезервированные домены).
- Telegram id ≥ 2^52 (таких аккаунтов не бывает), WhatsApp id — номер из диапазона выше `@s.whatsapp.net`.
- Нет триггеров, запусков, ИИ-заданий, напоминаний бота, загрузок звонков и токенов рекордера. Сообщения мессенджеров
  и письма — только записи истории: отправка в API синхронная и идёт только по нажатию кнопки, очереди «на отправку»
  в базе нет. У писем нет IMAP-uid (`email_id = NULL`): прочтение не ставит флаг на почтовом сервере.
- id мок-строк никогда не совпадают с id удалённых настоящих (см. выше): сессия Telegram/WhatsApp, папка FTP или
  кнопка бота удалённого сотрудника не достанется тестовому аккаунту.
- Проверки в транзакции (иначе `ROLLBACK`): у каждой сделки этап и ответственный-сотрудник, одна активная воронка со
  всеми системными этапами, у задач тип и конец не раньше начала, номера сделок уникальны и 1…N, история этапов
  упорядочена и совпадает со сделкой, закрыто ⇔ won/lost, причина проигрыша только у lost, события не раньше сделки
  и не в будущем, участники сообщений и письма истории существуют, нет триггеров/запусков/ИИ/напоминаний/загрузок,
  нет неотвеченных свежих сообщений, все телефоны/адреса/id в безопасных диапазонах, телефоны контактов уникальны,
  админ на месте, все мок-строки в своих диапазонах id, последовательности не отстают от строк. Внешние ключи
  проверяет сама база.
